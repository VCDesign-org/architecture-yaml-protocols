# メッセージング設計プロンプト集 (Messaging Design Collection)

非同期メッセージング（Pub/Sub, Queue）を利用するシステムの信頼性設計（到達保証、順序、冪等性）を行うためのプロンプト例です。

---

## 1. メッセージング設計のドラフト作成

システム要件から、KafkaやSQS/SNS等を用いた適切なメッセージング構成を設計します。

**Input:**
1. `specs/messaging-design-template.yaml` の内容
2. 以下のプロンプト

```text
あなたはクラウドアーキテクトです。添付のテンプレートに基づき、以下の決済処理システムの非同期メッセージング基本設計を行ってください。

### システム要件
- 概要: [ECサイトの注文を受け付け、在庫引当・決済・配送指示を行う一連のフロー]
- ユースケース: [注文完了メールの送信、外部決済サービスのWebhook受信]
- 要件:
  - 順序保証: [ステータス遷移（注文→決済済→発送）の順序遵守は必須]
  - 信頼性: [メールは最悪ロストしても良いが、決済データは絶対にロストしてはならない]
  - メッセージ量: [ピーク時 10,000 req/sec]

### 指示
- テンプレートの `model` で適切なブローカー(Kafka vs SQS)を選定してください。順序保証がネックになる点に注意してください。
- `consumer.idempotency` で、二重配送が発生しても多重決済されない仕組み（冪等性）を定義してください。
- `failure_handling` でのDLQ(Dead Letter Queue)戦略を具体化してください。
```

---

## 2. 信頼性レビュー

メッセージング特有の「罠」（順序逆転、二重処理、毒メッセージ）に対する対策が打たれているかチェックさせます。

**Input:**
1. 記入済みの `messaging-design-template.yaml`
2. 以下のプロンプト

```text
あなたはSREエンジニアです。
設計書をレビューし、メッセージング基盤の信頼性リスクを洗い出してください。

### チェック項目(Acceptance Criteria参照)
1. **冪等性(M01)**: メカニズム(`mechanism`)が具体的に定義されているか？「アプリ実装任せ」になっていないか？
2. **DLQ設置(M02)**: 処理不能なメッセージが溜まり続けてコンシューマーを詰まらせる(Poison Pill)対策ができているか？
3. **スキーマ互換性(M03)**: プロデューサーがメッセージ構造を変えた時、コンシューマーが壊れない戦略(`evolution_strategy`)になっているか？

### 出力
- スコア
- 改善が必要なリスク項目
```

---

## 3. 実装コード（Consumer Loop）の生成

コンシューマーの実装はエラー処理やAckのタイミングが難しいため、雛形を生成させます。

**Input:**
1. 記入済みの `messaging-design-template.yaml`
2. 以下のプロンプト

```text
あなたはバックエンドエンジニアです。
設計書に基づき、[Go]言語でのコンシューマー実装のスケルトンコードを作成してください。

### 実装要件
- **Graceful Shutdown**: SIGTERMを受け取ったら、現在処理中のメッセージが終わるまで待つこと。
- **Manual Ack**: 処理成功時のみAck（コミット）を行い、エラー時はNackまたはリトライすること。
- **冪等性チェック**: メッセージ処理の直前に、設計書の `idempotency.mechanism` に従った重複チェックロジックをプレースホルダーとして入れてください。
```
