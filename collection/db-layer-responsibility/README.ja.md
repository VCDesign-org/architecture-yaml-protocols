# DB責務設計プロンプト集 (DB Layer Responsibility Collection)

「DBは通過点であり、目的地ではない」という思想に基づき、データベースに過度な責務（ビジネスロジック、完全性保証、意味解釈）を持たせないための設計ガイドラインです。
特にIoTや大規模データ基盤において、DBがボトルネックやLock-inの原因にならないよう、疎結合なアーキテクチャを指向します。

---

## 1. DB責務と役割のドラフト作成

DBを「ただの保管庫（あるいは土管）」と定義し、周辺システム（EdgeやApp）に責務を寄せる設計を行います。

**Input:**
1. `specs/db-layer-responsibility-template.v1.yaml` の内容
2. 以下のプロンプト

```text
あなたはデータプラットフォームアーキテクトです。添付のテンプレートに基づき、以下のIoTデータ収集基盤のDB責務設計を行ってください。

### システム概要
- 目的: [世界中の工場から製造条件データを収集し、クラウドで一元管理する]
- 課題: [過去のシステムでは、DBにストアドプロシージャが大量にあり、スキーマ変更のたびに停止が必要だった。また、ネットワーク切断時のデータ欠損対応でDB側に複雑なリカバリ処理があった]

### 指示
- **役割の再定義**: `positioning.role` を "transit_point" とし、DBはデータの永続化のみに集中させてください。
- **入力側を強くする**: ネットワーク切断時の対策として、DB側で頑張るのではなく、Edge側でバッファリング(`input_requirements.buffering`)する設計にしてください。
- **工場の隠蔽**: 工場ごとの設備の違いを、DBスキーマで吸収しようとせず（`factory_agnosticism`）、汎用的なJSON等の構造で受け入れる設計にしてください。
- **ロジック追放**: ストアドプロシージャ等の独自機能を禁止(`proprietary_features: forbidden`)してください。
```

## 2. アーキテクチャ健全性レビュー

DBが「賢くなりすぎていないか（Fat DBになっていないか）」をチェックします。

**Input:**
1. 記入済みの `db-layer-responsibility-template.v1.yaml`
2. 以下のプロンプト

```text
あなたはクラウドネイティブ推進担当者です。
設計書をレビューし、DBが将来のシステムリプレースやスケーリングの足枷にならないか診断してください。

### 診断ポイント (Acceptance Criteria参照)
1. **ストアド依存 (DB04)**: ビジネスロジックがDB内に埋め込まれ、アプリと密結合になっていませんか？
2. **意味の混入 (DB03)**: 「この値が良品判定基準である」といった解釈(Meaning)がDBのカラム定義に含まれていませんか？（Factのみ保存されていますか？）
3. **エッジの弱さ (DB02)**: DBが落ちたらデータロストする設計になっていませんか？（Edge側でStore & Forwardが担保されていますか？）
4. **スキーマ依存**: 新しい設備が入るたびに `ALTER TABLE` が必要な設計になっていませんか？

### 出力
- アーキテクチャ健全性スコア
- 疎結合化への改善提案
```

## 3. 実装方針（Edge/DB分離）の生成

DB自体ではなく、「DBを守るためのEdge側実装」や「DBを使わないデータ利用ロジック」を生成させます。

**Input:**
1. 記入済みの `db-layer-responsibility-template.v1.yaml`
2. 以下のプロンプト

```text
あなたはIoTエッジエンジニアです。
設計書の `input_requirements` に基づき、クラウドDBへの送信クライアント(Go言語)の設計コードを作成してください。

### 実装要件
1. **バッファリング**: 送信失敗時、メモリまたはローカルディスクにデータを一時保存するキュー構造。
2. **正規化**: 送信前にデータをバリデーションし、DBが期待する「汎用フォーマット」に変換するロジック。
3. **リトライ戦略**: 指数バックオフを用いて、DB復旧後に優しく再送する処理。
```
